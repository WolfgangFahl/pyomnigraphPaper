%% Abstract (author-provided text).
\begin{abstract}
The challenges of federated queries that came up in the following use cases led to the need to be able to work with subgraphs of the RDF graphs and try out different alternative endpoints such as QLever, Virtuoso and others. Wikidata is an example of a very large, crowd-sourced general knowledge graph backed by a worldwide community since 2012. FactGrid has been using the same Wikibase infrastructure as Wikidata since 2017 for historical research projects. GOV (Geschichtliches/Genealogisches Ortsverzeichnis) is an online gazetteer for searching ancient places. Wikidata grew so large that the Blazegraph endpoint powering it was pushed to the 4 terabyte limit and the Wikimedia Foundation therefore decided to split the knowledge graph to host two instances.
While typical research projects that do such subgraphing and benchmarks roll their own environments, our pyomnigraph, a Python-based open source library, provides a unified infrastructure with a standard set of REST APIs and CLI commands to improve the handling and potentially grow the matrix of subgraphs versus endpoints to work with.
In this work we report on pyomnigraph usage on seven graphs, four endpoints and three use cases with four example queries each, spanning three different graphs per use case. This opens a multidimensional space for exploring different combinations of federated queries, starting from a natural remote-remote-remote federated query to the possible combinations of local federated queries backed by all endpoints supported by pyomnigraph. We show that typical frustrations of scaling multi-hop federated queries can be avoided if the subgraphs are locally loaded and federation is applied locally.

\end{abstract}

\section{Introduction}\label{sec:introduction}
Wikidata~\cite{Vrandecic2014} started in 2012 as an effort to back the different multilingual Wikipedia sites with a common set of facts. By the end of the year, 2149719 entities were harvested from existing Wikipedia content, this initial phase ended in February 2013 with 4 million items. As of 2026, over 100 million entities have been curated by a growing worldwide community of contributors. In 2022, we reported on \emph{Getting and Hosting Your Own Copy of Wikidata}~\cite{fahl2022wikidata}. For quite a few use cases, the need for federated queries based on subgraphs of diverse public and internal knowledge graphs has been our motivation to try out different combinations of endpoints and subgraphs. In the case of Wikidata, we have even been forced to do so by the 2025 graph split~\cite{willighagen2026scholia}.

Public alternatives to the official Wikidata Query Service WDQS are still rare. Our attempts to convince the Wikimedia Foundation to support a public mirror infrastructure have so far been unsuccessful.

\footnotelink{https://nicescholia.wikidata.dbis.rwth-aachen.de/api/endpoints}{nicescholia}~\cite{nicescholia} to be watched as potential alternative Scholia backends.

The Wikimedia Foundation itself now serves three: the
\footnotelink{https://query-legacy-full.wikidata.org/sparql}{legacy full graph} and, since the
WDQS graph split, a \footnotelink{https://query-main.wikidata.org/sparql}{main} and a

Using federated queries on participants of the Linked Open Data Cloud \footnotelink{https://lod-cloud.net}{LOD Cloud} is in theory an excellent way to answer queries over diverse data sources. In practice, there are a lot of possible frustrations involved, such as outages of endpoints, incompatibilities of endpoints, awkward syntax and general query rot.

For real-life use cases that operate on small subgraphs only, it should be feasible to operate locally by providing the necessary data \tquote{on the fly}. Unfortunately, to do so, a lot of technical expertise is needed to set up endpoints, collect the subgraph data and finally perform the query. 
To ease this pain, we introduce pyomnigraph, which mitigates the complexity by using Docker and Python to provide a unified interface to different endpoint technologies in a local environment with limited resources.

The contributions of this work are:
\begin{itemize}
\item \textbf{pyomnigraph architecture}, a blueprint of components that separate concerns of data operations, server management and endpoint backends using Docker containers, see Figure~\ref{fig:architecture}.
\item \textbf{pyomnigraph}, an Apache-2.0 licensed Python library that unifies the deployment and operation of multiple RDF triple stores behind a single API and Docker-based setup (Section~\ref{sec:resource}), covering the backends listed in Section~\ref{sec:backends} and the \texttt{omnigraph} and \texttt{rdfdump} command-line interfaces (Section~\ref{sec:cli}).
\item \textbf{demo survey of working dataset and endpoint combinations}, see Tables~\ref{tab:backends} and \ref{tab:subgraphs}.
\item \textbf{RRR versus LLL federated query comparison}, a measured comparison of remote-remote-remote (RRR) against local-local-local (LLL) placements of three-leg federated \texttt{SERVICE} queries across four local backends, including the executor versus \texttt{SERVICE} target compatibility matrix and engine-specific failure modes (Section~\ref{sec:evaluation}, Tables~\ref{tab:llldiagonal} and \ref{tab:servicematrix}).
\end{itemize}

\section{Related Work}\label{sec:relatedwork}
\paragraph{Wikidata graph split}
Willighagen et al.~\cite{willighagen2026scholia} report on the three options that have been considered for handling existing queries after the 2025 Wikidata graph split: federated queries between the main and the scholarly graph, using QLever~\cite{bast2017qlever} with modified queries on a full graph that does not suffer from the 4 TB limit of the Blazegraph endpoint, or using the snapquery named-parameterized-query middleware~\cite{snapquery} to separate the endpoints' concerns from the domain needs.

\paragraph{Wikidata subsetting}
Hosseini Beghaeiraveri et al.~\cite{hosseini2023subsetting} survey approaches,
tools and evaluation of Wikidata subsetting. Table~1 of the survey lists
SPARQL CONSTRUCT queries as a separate tool category stating \tquote{Requires full
dump} --- a statement we do not agree with: access to a live SPARQL server
is sufficient.

\paragraph{Linked Data Fragments}
The Linked Data Fragments line of work addresses the same pain point --- public SPARQL endpoints cannot sustain highly concurrent live query workloads --- with a different infrastructure approach: smart-KG~\cite{azzam_smartkg_2024} ships pre-materialized, compressed graph partitions from the server to the client for client-side evaluation, and Heling and Acosta~\cite{heling_framework_2021} provide a framework for federated SPARQL query processing over heterogeneous Linked Data Fragments.
% Predecessor 2022 paper, RDF triple stores, SPARQL 1.1 federation, benchmarking.

\paragraph{CONSTRUCT queries}
CONSTRUCT queries in SPARQL have been studied by Kostylev et al.~\cite{kostylev2015construct}: the nearly identical syntax of CONSTRUCT and SELECT queries --- both share the same WHERE clause --- is \tquote{often deceptive}. The issues to beware of are (1) the output domain --- partial mappings for SELECT versus RDF graphs for CONSTRUCT --- (2) blank nodes in templates, which CONSTRUCT allows while they are unavailable in SELECT, and (3) unbound variables that are silently dropped.

% federated queries
\paragraph{Federated SPARQL query processing}
Federated SPARQL query processing evaluates a single query over data that is distributed across several \emph{remote SPARQL endpoints}~\cite{prudhommeaux2013federated}.
What counts as a correct answer is defined by comparison with the centralized case.
A federated query must return exactly the result that the same query would return over a single RDF graph holding the data of all participating endpoints~\cite{aimonier-davat_fedup_2024,heling_federated_2022}.
The difficulty is that this answer has to be produced without such a graph ever existing, and while contacting as few endpoints as possible.
Two rather different mechanisms are commonly subsumed under the term, and they differ in who decides how the query is distributed.
 The first is part of the standard: SPARQL~1.1 provides the \texttt{SERVICE} keyword, which instructs a federated query processor to evaluate a designated part of a query against a designated remote endpoint and to combine the results it returns with those of the remaining parts~\cite{prudhommeaux2013federated}.
 Because the endpoint URLs are written into the query text, the author fixes the distribution in advance and the processor only dispatches what it is told.
 The second is a \emph{federation engine}, a system layer built on top of the standard, which accepts an ordinary SPARQL query carrying no endpoint annotations, together with a catalogue of reachable endpoints, and derives the distribution itself.
 It does so in three stages (source selection and query decomposition, optimization, and execution), and engines differ mainly in how much knowledge the first stage draws on: zero-knowledge probing with \texttt{ASK} queries (FedX), precomputed indices or VoID summaries (SPLENDID, HiBISCuS, CostFed), or runtime adaptivity (ANAPSID)~\cite{heling_federated_2022,hameurlain_selection_2016,saleem_largerdfbench_2018}.
 Throughout, the decisive optimization is the detection of \emph{exclusive groups}, subqueries answerable by a single endpoint, which collapse many requests into one.
 The sources of a federation need not even be full SPARQL endpoints: interfaces of more restricted expressivity, such as triple pattern fragments, give rise to \emph{heterogeneous} federations~\cite{heling_federated_2022}.
 It is the automatic derivation of the distribution, rather than the delegation mechanism itself, that the results discussed below call into question.
\paragraph{Benchmarks}
Performance is assessed with benchmarks: FedBench has long been the reference~\cite{hutchison_benchmarking_2012}, LargeRDFBench scales it to a billion triples with complex and large-data queries~\cite{saleem_largerdfbench_2018}, FedShop scales the number of participating endpoints from 20 to 200~\cite{payne_fedshop_2023}, QFed generates query sets dynamically for specialized systems~\cite{rakhmawati_qfed_2014}, FQCEB targets cardinality estimation~\cite{xu_evaluation_2023}, and FKGQA extends the setting to federated question answering~\cite{dobriy_agentic_2026}.
 FedBench alone, however, cannot expose the problem at hand: all of its queries decompose into at most three subqueries, so every engine behaves alike on it~\cite{hameurlain_selection_2016}, and with a mean of 4.3 triple patterns and runtimes of roughly two seconds its results do not extrapolate to the Data Web~\cite{saleem_largerdfbench_2018}.

\paragraph{Alternative tooling}
An obvious alternative to pyomnigraph is the hand-rolled setup: benchmark and evaluation projects routinely build their own Docker compose files, store-specific loaders and engine control scripts, and the prevailing answer to the question of the best tooling tends to be \tquote{my own}. Even the triple store authors themselves maintain per-engine control tooling rather than a cross-engine toolchain. pyomnigraph replaces this per-project fragmentation with one declarative subgraphs-versus-backends matrix; the direct feedback we received from triple store authors on this approach is tracked in our repositories.

\section{The pyomnigraph Resource}\label{sec:resource}
pyomnigraph~\cite{pyomnigraph} provides a unified Python interface for multiple graph databases. The software is open source under Apache 2.0 license and hosted on GitHub.
Figure~\ref{fig:architecture} shows the architecture in one panel: the \texttt{omnigraph} and \texttt{rdfdump} command line interfaces and the planned REST API (future work, see Section~\ref{sec:conclusion}) share the unified Python API, which manages the triple store backends as Docker containers; \texttt{rdfdump} pulls subgraph dumps from public SPARQL endpoints.

pyomnigraph leverages the named parameterized query approach from the snapquery~\cite{snapquery} framework, which handles such parameterized SPARQL queries. It supports semantic annotation of queries and monitoring of their execution. By abstracting away the underlying endpoint, it can call multiple endpoints at once to compare results, or swap endpoints transparently, without users noticing or having to change anything.

The same separation of concerns---hiding details of endpoints and queries---is used by pyomnigraph. For human readability, you will find YAML versions of these details in the \texttt{examples/<usecase>/} folders of our paper repository.

\subsection{Command-Line Interfaces}\label{sec:cli}
There are two command line interfaces available for pyomnigraph: \texttt{omnigraph} for server management and \texttt{rdfdump} for data operations.

The two core options are:
\begin{lstlisting}[caption={omnigraph core options},label={lst:omnigraph-options}]
--cmd CMD [CMD ...]   commands to execute on servers: bash, clear,
                      count, info, load, logs, needed, rm, start,
                      status, stop, upload, webui

-s SERVERS [SERVERS ...], --servers SERVERS [SERVERS ...]
                      servers to work with - 'all' selects all
                      configured servers [default: ['blazegraph']]
\end{lstlisting}
so that multiple commands can be combined to be run on multiple servers.

The core options of \texttt{rdfdump} are:
\begin{lstlisting}[caption={rdfdump core options},label={lst:rdfdump-options}]
-ds DATASETS [DATASETS ...], --datasets DATASETS [DATASETS ...]
                      datasets to work with - all is an alias for
                      all datasets [default: ['wikidata_triplestores']]

--dump                perform the dump [default: False]

-4o, --for-omnigraph  store dump at default omnigraph location
                      [default: False]
\end{lstlisting}
The design of the two tools is to make them available as a single
toolchain --- see the loop usage in Listing~\ref{lst:railway-load}.

\section{Use Cases and Data Sources}\label{sec:datasources}
%The use cases for our experiments are motivated by the eat your own dog food approach.
Three use cases are the basis for our demonstration and evaluation: papers and authors (scholarly), historical locations for genealogy research, and railway journey planning. 
For each use case, we specify a list of information needs, from which we derive concrete example queries. The abstraction is then done by applying named parameterized queries.

\subsection{Method}\label{sec:method}
Our query development is issue driven in the
\footnotelink{https://github.com/WolfgangFahl/pyomnigraphPaper/issues/2}{query workflow issue}
of the paper repository. For each use case, the authors provided the information
needs and the raw initial queries from the use case sources as the initial prompt.
Agentic AI then worked on per-query sub-issues to provide the different forms of
each query: the endpoint-checked and potentially adapted named parameterized
query, its Count and Histogram companions, and the CONSTRUCT version as a
pyomnigraph dataset declaration, starting from the
\footnotelink{https://github.com/WolfgangFahl/pyomnigraphPaper/issues/8}{dataset declaration issue}.
Acting as a research assistant, the agentic AI checked the queries and documented
the results in the query issues. The evaluation experiments of
Section~\ref{sec:evaluation} were run the same agentic way, tracked in issues
\footnotelink{https://github.com/WolfgangFahl/pyomnigraphPaper/issues/24}{\#24} to
\footnotelink{https://github.com/WolfgangFahl/pyomnigraphPaper/issues/28}{\#28}.

Table~\ref{tab:subgraphs} shows the subgraph sources for the use cases.

Table~\ref{tab:usecasequeries} tracks the named parameterized queries that we use to demo and benchmark, one row per query and example binding. Each query is defined
in \texttt{examples/<usecase>/queries.yaml} with its parameter list and default values, each endpoint in \texttt{examples/<usecase>/endpoints.yaml}, so a row is reproduced by a single \texttt{sparqlquery}~\cite{pylodstorage} call; the \texttt{query.sh} script of each use case reruns all its queries and writes a \texttt{<QueryName>.md} result file per query.

\section{Evaluation}\label{sec:evaluation}
% Results across store and endpoint combinations.
By applying the matrix approach of Section~\ref{sec:benchmark}, we obtain interesting results on performance and failure cases. We then do a comparison of remote-remote-remote versus local-local-local federated queries across all possible combinations.

Federation works cleanly for the remote-remote-remote and local-local-local  placements on three of the four backends, with a set of specific failure modes which we collected in the
\footnotelink{https://github.com/WolfgangFahl/pyomnigraphPaper/issues/16}{failure cases issue}
of our paper repository. The $4^3 = 64$ off-diagonal grid is feasible for the executors Apache Jena, Oxigraph and QLever per the pair matrix --- roughly a 10-minute run on a MacBook Pro 2.4 GHz 8-core with 32 GB of RAM; structural failures have been found with Blazegraph as reported in our GitHub repository.

Table~\ref{tab:llldiagonal} shows the RRR baseline over the public origin endpoints and the LLL diagonal --- all three SERVICE legs of each federated query on the same local backend --- with the record counts of the \texttt{Count} companion queries and the query-only latency. Apache Jena, Oxigraph and QLever reproduce exactly the RRR record counts (AuthorIdentity 1, PlaceIdentity 3, LineIdentity 1). Blazegraph answers PlaceIdentity with 81 instead of 3: it re-evaluates uncorrelated SERVICE legs per outer solution and multiplies their results --- two-leg probes yield $9/9/1$ where $3/3/1$ is expected; AuthorIdentity and LineIdentity mask the defect because every leg returns a single row.

\section{Conclusion and Future Work}\label{sec:conclusion}
As this is a resource paper, we have been pragmatic about the subtle differences between CONSTRUCT and SELECT queries pointed out by Kostylev et al.~\cite{kostylev2015construct}: the shared WHERE clause even led us to name the extraction pattern of our dataset declarations \texttt{select\_pattern}. A formal analysis of the limitations of this pragmatic approach would be beneficial to avoid trial and error for use cases that are out of bounds of our approach.

The RESTful interface of the architecture (Figure~\ref{fig:architecture}) is future work: it is most interesting for agentic AI work, e.g. as an MCP service backend.
